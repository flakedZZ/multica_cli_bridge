# 运维与故障恢复

## 状态位置

- 桥接 `state/tasks.sqlite3`：请求归属、讨论轮次、执行父单映射、交付快照与 ack；确认回读失败写入 `confirmation_checks`。
- 插件数据目录 `deliveries.sqlite3`：文本/图片发送记录、完整结果收件、原文件字节和 QQ 文件回执。
- `execution_pending.json`、`mika_pending.json`：待交付任务与待方案轮询。
- 插件 `dialogue_bindings.sqlite3`：可信用户、原会话、原消息、讨论 ID、轮次、版本及状态；方案唤醒后仍保留，重启可恢复。不得作为普通缓存删除。

这些数据用于防重复，不能当作随时可删除的缓存。

## 重启后找回未确认任务

调用工具 `multica_mika(action="pending")`，从桥接 SQLite 持久记录查询当前用户、当前会话的未确认讨论；不依赖内存或 `mika_pending.json`，也不访问远端、建单或发送消息。每页最多 10 条，按 `has_more/next_cursor` 分页。这里只反映桥接本地状态，远端已关闭或被其他需求替代的旧讨论仍可能出现，不应批量确认。

拿到原 `dialogue_id` 后调用 `plan`：waiting 可继续查询，question 先澄清，proposal 阅读完整方案并确认仍符合原需求后，带原 `version` 与 `review` 调用 confirm。uncertain/confirming 列为 manual_check，先核对已有执行编号及写入结果，不重新 discuss。

pending、plan、confirm、cancel 都接受宿主可信用户身份；缺少可信身份时使用本人当前查询消息即可，不要求最初消息仍在最近消息窗口。讨论归属、版本、审核与原生父子校验继续由桥接执行。恢复确认成功后，插件仍会保存执行结果跟踪并按回执收尾。

## 常见问题

**查询缺少身份**：无可信调用者的群聊需要当前查询者自己的完整消息 ID。通过宿主按 ID 读取并验证消息；不能使用同群其他人的消息。

**拿不到附件下载地址**：模型不需要链接。确认最终评论声明的文件已作为实际附件上传，查看桥接下载/交付错误。文件经认证 CLI 下载到桥接，再传输字节；不要向 QQ 暴露认证链接。

**方案已返回但 confirm 无法继续**：confirm 必须提供已审核方案的准确 `version` 和非空 `review`，`dialogue_id` 可省略。插件使用可信宿主身份/已验证消息得到的本人、本会话与持久版本关联补齐 ID，随后通过 `plan` 校验最新归属和版本，再发送带真实 ID 的 `confirm_plan`。不会按最近任务或仅凭待确认摘要执行。升级前没有本地关联时，插件分页查询 `pending`，只接受唯一准确版本，再读取完整方案校验。多个匹配、版本失效或无匹配时返回可操作错误：`pending → 明确选择原dialogue_id → plan → 审核 → confirm`；显式 ID 也不能绕过归属及版本校验。

审核是 QQbot 内部检查，原需求明确且已授权时无需用户再确认。服务端唯一版本定位兜底保留，以兼容旧客户端。确认超时后可携带同一版本重试：已知执行单只回读原单，未知创建结果由服务端拒绝重建；不要重发 discuss。插件的绑定保存与远端请求在同一串行锁内，避免本机并发新需求覆盖已有版本关联。其他客户端的并发修改仍由服务端最终版本校验拒绝。

**模块启动下参数错误变成 HTTP 500**：`python -m bridge.server` 的入口与 `bridge.server` 导入模块身份不同。请求校验和 `BridgeError` 统一放在 `bridge.validation`，避免合法的参数拒绝被当成内部异常。部署时必须包含新文件 `bridge/validation.py`。

**confirm 结果不明**：已知执行 UUID 会保留，后续确认只回读原单。完全未知的创建结果需要管理员用 CLI 查证，不可删除 pending 后盲目重建。

**父单缺失/不匹配**：先核实讨论单是否删除、执行单原生 parent 和本地 execution_links 是否一致。恢复时停插件/桥接并备份，通过 CLI 修改已核实的原生关联，再以事务精确更新唯一匹配的本地映射，保留旧 UUID 和变更依据。替代父单需明确授权，不指派新的执行工作。禁止移除 execution_links 来绕过新版交付检查。

**文件 pending/uncertain**：上传超时、进程中断或不完整回执都不证明 QQ 未收到。先查 QQ 文件/聊天记录及适配器回执，以原目标、附件 ID、名称、字节数和 hash 对账；取得原始成功回执则恢复确认并复用。没有足够证据时保留待核对，不能定时重发。

## 升级与回滚

1. 核对当前源码、宿主/SDK版本、配置和待处理工作，避免覆盖并发改动。
2. 停用插件与桥接。两端停止写入后备份代码、配置、数据库和 pending 文件；凭据备份只放私有位置。
3. 部署已验证代码；宿主身份补丁变更需要重启宿主，仅热加载插件不够。
4. 验证文件 hash、数据库完整性、桥接健康、插件注册、用户/会话拒绝和回执保留，再恢复处理。
5. 回滚代码/配置时保留最新数据库（包括新增 dialogue_bindings.sqlite3）和成功回执。旧插件不读取新增绑定库，可原地保留；无桥接库迁移。不能用升级前的旧库覆盖已交付业务，否则可能重复发送。

历史文件补发必须有明确授权，先核对成功/不明回执及 QQ 侧记录，只恢复原用户和原会话的唯一 job。不要重新派任务生成同样内容。若内容和附件已改变，应重新核对交付快照，不能让旧回执覆盖新版本。

## 传输边界

图片使用 SDK 发送路径。普通文件通过适配器公开 API，以 `base64://` 传字节，避免将某容器本地路径冒充另一容器可见路径。文件以数据形式传输，不执行 HTML 或附件代码。

成功要求完整上传/发布 action 的 `status=ok`、`retcode=0` 和非空 `file_id`。仅下载完成、文本通知、请求发出或等待超时均不是文件送达证明。结果正文和所有附件回执齐全后才允许自动完成父子单。
